commit e245ac0a19080dd922d47fe1f0d56eb7d4ee0fe1
Date:   2026-10-09

feat(storage): add a durable append-only review store and wire the UI write path (issue #12)

The UI announced on every page that it could not record a human decision, because no durable
store existed to append to. This adds one and connects the single approved write path. It is the
last open acceptance criterion of Milestone 8.

## The store

`src/aegistrace/storage/reviews.py` adds `ReviewStore`, an append-only DuckDB store. It issues
only `CREATE`, `INSERT` and `SELECT`, so no mutation code path exists in the codebase at all;
`review_id` is a primary key; and every read reconstructs a `ReviewHistory` so a hand-edited
database fails loudly instead of presenting a forged lineage as authoritative.

An append-only head journal records the head review and the count. It exists because probing
found a real gap: deleting the **newest** review leaves a shorter but internally-valid chain that
`validate_chain_is_linear` cannot see, so the store would silently lose the most recent human
decision - the worst failure an evidence-custody tool could have.

The honest limit is stated rather than implied: DuckDB does not make a table immutable, so a user
with the `duckdb` CLI can still issue `UPDATE`/`DELETE`. Tampering is **detected, not prevented**.
Preventing it is what PostgreSQL with restricted roles would buy, and PostgreSQL stays deferred.

`reviewed_at` is stored as a VARCHAR ISO-8601 string: DuckDB `TIMESTAMP` is timezone-naive and
`TIMESTAMPTZ` needs `pytz`, and neither is worth a dependency for a value we only ever order.

## The write path

`POST /decision` appends a `HumanReview` when a store path is configured, and refuses visibly
when it is not. The refusal distinguishes two genuinely different situations, because collapsing
them would itself be a false statement:

    an append that FAILED          -> "Nothing was written."
    an append that SUCCEEDED but
    whose read-back failed         -> "The review WAS appended, but the store could not read the
                                       history back to confirm it."

An earlier read-back-after-append helper was **deleted rather than repaired**: it reported success
after re-reading, which makes the phrase "nothing was written" potentially false in the second
case above.

`scripts/run_local_ui.py` gained `--store` and still exposes **no `--host` flag**. A missing store
directory is refused with exit 2 *before* a socket is opened, for the same reason the artifact is:
a store started at a mistyped path would make "no reviews yet" indistinguishable from "wrong
place".

## Dependency shape

`duckdb` is declared under a **new optional `storage` extra** and imported lazily inside `open()`,
so the research library never depends on a database engine. A test asserts `duckdb`, `fastapi` and
`uvicorn` are absent from core `dependencies` structurally, by parsing `pyproject.toml`.

feat(ui): implement the approved local investigation instrument (issue #12)

Implements the UI direction the owner approved: Investigation Bench (C) as the shell, Chain of
Custody (A) as the provenance view, Two Witnesses (B) as a dedicated AI-assessment comparison
view, in the owner's investigator order findings -> evidence -> AI comparison -> review
requirements -> human decision. This is the last unstarted item in the objective.

## What is implemented

`src/aegistrace/ui/` (read layer + app), `scripts/run_local_ui.py`, five Jinja templates and one
CSS file. No JavaScript at all, so the instrument works with JS disabled. All assets local: no
CDN, no web font, no external image, no telemetry.

The UI performs **no detection, no scoring, no ranking and no tier classification**. Tier
assignment stays in `classify_tier`. The UI renders what the pipeline already computed.

## Two honesty properties, enforced in code rather than in prose

1. **A missing or malformed artifact RAISES; it never becomes an empty view.** An empty screen and
   a broken screen must not look the same. `ArtifactUnavailableError` names the path and the
   reason, and the page renders that reason rather than "no findings" - which would be a claim
   about the evidence rather than about the plumbing. The genuinely-empty-but-valid artifact is
   the boundary case and is tested separately, because it must NOT raise.
2. **The synthetic flag is read, never inferred from the data.** `synthetic` is the artifact's own
   `providers_configured` declaration, and the artifact's `warning` is surfaced verbatim on every
   page in a persistent, non-dismissible, text+shape banner.

## What it deliberately does NOT do, and says so on the page

- **It does not save a human decision.** Appending a `HumanReview` needs a durable store to append
  to and none exists, so `POST /decision` returns an explicit "NOT recorded" page. A form that
  silently discarded a human decision would be the worst failure an evidence-custody tool could
  have.
- **It never invents an assessment pair.** The comparison view always reports "AI assessment not
  available", because the artifact carries no assessments and no real (non-synthetic) run exists -
  the provider freeze is `BLOCKED_HUMAN`.
- **An unknown record id does not fall back to a different record.** Showing case B when case A
  was asked for is a substitution, not a convenience, so it renders "no such record".

## Loopback-only, made structural

`scripts/run_local_ui.py` exposes **no `--host` flag at all** and binds one constant, `127.0.0.1`.
A documented-only constraint is enforced by whoever reads the documentation; this one is enforced
by the absence of the flag.

Verified live, not asserted: with the server running, `http://127.0.0.1:8791/findings` returned
**200** while the machine's LAN address `192.168.2.245:8791` was **refused**, and nothing was bound
to `0.0.0.0`. A missing artifact is refused with a non-zero exit *before* a socket is opened,
because a server that starts and then shows "unavailable" makes the operator believe it works.

## Dependency shape

FastAPI/uvicorn/jinja2/python-multipart are declared under a **new optional `ui` extra**, never in
`dependencies`. The research library must not need a web server: detection, triage, tiering and
review all work headless, and a reader who only wants the library should not install a server. A
test asserts this structurally against `pyproject.toml`.

commit 3b3fbceef8637a808a5528a94a9b6cd3cd87d816
Date:   2026-10-08

feat(review): reconcile the tier a review CONDUCTED against the tier required (issue #30)

Owner decision, verbatim: "Approve Option 1. HumanReview.tier represents the tier actually
conducted; TierAssignment retains the tier required. Reconcile the two, report unmet
requirements explicitly, and do not assume a simple numerical ordering of tiers. Preserve
review history and add regression tests."

Before this, `HumanReview.tier` carried a tier that nothing ever compared to the
`TierAssignment.tier` for the same case. A case that REQUIRED expert judgement but was only
machine-checked was silently accepted.

## Meaning fixed, field not renamed

`HumanReview.tier` is the tier ACTUALLY CONDUCTED - the level of human scrutiny the reviewer
really applied. `TierAssignment.tier` is the tier REQUIRED. The field is not renamed and
`review_id_for`'s inputs are unchanged, so stored records still load and the append-only
history chain is untouched.

## The relationship is explicit and NON-ORDINAL

`_REQUIREMENT_SATISFIED_BY: dict[ReviewTier, frozenset[ReviewTier]]`

    A <- {A, B, C}
    B <- {B, C}
    C <- {C}
    D <- {D}

`D_INSUFFICIENT_EVIDENCE` is its own case and is NEVER treated as "more than C". It is a
terminal *outcome* - the evidence did not support a decision - not a qualification level. So:

  - a D-conducted review does NOT satisfy an A, B or C requirement;
  - a C-conducted review does NOT satisfy a D requirement;
  - a D requirement is met only by a D-conducted review.

Exposed as `tier_satisfies_requirement(*, conducted, required)`, which reads the map so the
map is the single source of truth.

## Enforced on the schema, not in a helper

New `TierReconciliation(FrozenSchema)` owns BOTH halves - `assignment` (required) and `review`
(conducted) - with two `model_validator(mode="after")` methods. This placement is the point:
this project's documented read-path hazard is that a rule written once in a builder is bypassed
by `model_validate`, which is how durable records are read back.

`reconcile_tier` recomputes `requirement_met` and `unmet_requirement` from the two authoritative
tiers on EVERY construction path - construction, `model_validate` of stored JSON, and
`model_copy(update=...)` (which `FrozenSchema` re-validates). A stored record that claims a
satisfied requirement its tiers contradict is REFUSED, and a forged `unmet_requirement` note is
overwritten rather than trusted.

**Under-review is recorded, not fatal.** An under-reviewed case produces a valid object with
`requirement_met=False` and a plain-language `unmet_requirement` naming both tiers. That makes
the discrepancy an inspectable, serialized, immutable fact rather than a silent acceptance or a
crash - and it still lets a human escalate a case the assigned tier never covered.
